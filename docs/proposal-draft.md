# Proposal draft — Reconstruct a document from its editor undo journal

DRAFT for Jyoti to edit into her own voice before submitting.

---

## Task summary (one line)

Given a saved text document and the append-only operation journal its editor
recorded while it was being written, reconstruct the document's original state
byte-for-byte.

---

## 1. The difficulty — what the task is and why it is genuinely hard

The agent is given three things in `/app`: the final saved document, the
editor's operation journal (a few hundred entries), and a written specification
of the journal format. It must produce the document as it existed before the
first recorded edit.

The journal is append-only and records what a real code editor records: insert
and delete operations, each carrying a position and the affected text, plus
undo/redo bookkeeping. Replaying it forward reproduces the final document.
Reconstructing the original requires inverting it — and the inversion is not
symmetric with the forward direction, which is where the difficulty lives.

Four properties, all documented in the spec but each easy to mishandle, make a
naive inversion produce a document that is plausible and wrong:

**Positions are relative to intermediate states.** Every entry's offset refers
to the document as it existed at the moment that entry was applied, not to the
final document. The journal is therefore only invertible by walking it strictly
backwards, applying each inverse to the state produced by the previous inverse.
Any attempt to compute final-document offsets up front, or to process entries in
document order rather than journal order, silently corrupts everything before
the first mistake.

**Offsets are UTF-16 code units, not bytes and not characters.** This is what
real editors do — VS Code, the LSP wire protocol, and the browser DOM all count
in UTF-16. The document is UTF-8 and deliberately contains emoji and CJK text.
An emoji outside the Basic Multilingual Plane occupies two UTF-16 code units,
one Python character, and four UTF-8 bytes. Any of the three natural readings of
"position" is therefore wrong for a different subset of the document, and the
error only manifests after the first non-ASCII character in the file. A solution
that assumes byte offsets works perfectly on the ASCII prefix and drifts
thereafter.

**Undone edits are present in the journal but absent from the document.** The
journal is append-only, so operations the user performed and then undid are
still recorded, followed by an undo marker. Those operations never contributed
to the saved state. The effective operation sequence must be derived from the
raw journal before any inversion is attempted; inverting the raw sequence
removes text that was never there.

**The document was normalised on save.** The editor wrote the file with a
line-ending normalisation applied at save time, so journal offsets refer to the
pre-normalisation text. The offset space and the on-disk byte space are not the
same coordinate system, and the discrepancy grows with every line.

Each of these is individually tractable. The difficulty is that they interact:
the correct order of operations is to resolve the undo structure, then convert
coordinate systems, then invert — and a solution that does these in the wrong
order produces output that is nearly right. Because the agent has no reference
copy of the original, it has no way to detect that it is wrong. It cannot
self-check, cannot bisect, and gets no error — just a confident, subtly
incorrect document.

This is the day job of engineers who build editors, operational-transform and
CRDT synchronisation engines, and collaborative editing backends. Undo-stack
inversion and UTF-16 offset arithmetic are exactly the class of bug that ships
in those systems.

**Data provenance.** Everything is synthetic and generated by a script I write.
The document is assembled from generated prose containing a controlled mix of
ASCII, CJK, emoji, and combining characters; the journal is produced by applying
a seeded pseudo-random edit sequence to it. The answer therefore exists nowhere
online and cannot be retrieved, only computed. The generator uses a fixed seed,
so the task is fully deterministic and reproducible.

---

## 2. The intended approach and the key insight

**The key insight:** the journal must be reduced to an effective operation
sequence and translated into a single coordinate system *before* inversion
begins. Solutions that invert first and correct afterwards cannot recover,
because each mis-positioned inverse corrupts the state that the next inverse
depends on.

The approach, in four stages:

1. **Resolve the undo structure.** Walk the journal forward, maintaining a
   stack. Undo markers invalidate the operations they refer to; those operations
   are dropped. What remains is the effective sequence that actually produced the
   saved document.

2. **Establish the coordinate system.** Recognise that offsets are UTF-16 code
   units and that the saved file has been line-ending normalised. Reconstruct the
   pre-normalisation text so that journal offsets and text positions agree, and
   build a conversion between UTF-16 code-unit offsets and native string indices
   that is correct for astral-plane characters.

3. **Invert backwards.** Walk the effective sequence from last to first. An
   insert of text T at offset P is undone by deleting the characters at that
   span; a delete of text T at offset P is undone by reinserting T there. Each
   inverse is applied to the state produced by the previous one. Compound
   (coalesced) entries expand into their constituent operations and are inverted
   in reverse order internally.

4. **Denormalise and write** the reconstructed original to `/app/original.txt`.

A senior engineer who already holds this insight — that is, who knows to
resolve undos first, and who recognises the UTF-16 offset convention on sight —
would implement and debug this in roughly **3 focused hours**. The bulk of that
time is the coordinate conversion and verifying the undo resolution against the
spec's edge cases, not the inversion loop itself, which is short.

I hold this solution. The generator produces the original document first and
derives the journal from it, so the reference answer is known by construction
and the reference solution is validated by comparing its output against the
document the generator started from.

## 3. How it will be verified

The agent must write exactly one artifact: `/app/original.txt`.

Verification is deterministic and exact. The test suite holds the SHA-256 digest
of the true original document, computed at task-authoring time and stored inside
`tests/` — which is added only at verify time and is not present during the
agent run, so the answer is never on a path the agent can read. There is no
tolerance and no partial credit on the primary criterion: the reconstructed file
either hashes to the expected value or it does not.

Test functions, one per criterion:

1. `/app/original.txt` exists and is valid UTF-8.
2. Its byte length equals the expected length.
3. Its SHA-256 digest equals the expected digest — the exact-match criterion.
4. The input files `/app/document.txt` and `/app/journal.jsonl` are unmodified,
   verified against their own digests, so the agent cannot pass by rewriting its
   inputs.
5. Replaying the effective journal forward over the submitted `original.txt`
   reproduces `/app/document.txt` exactly — an independent structural check that
   confirms the answer is consistent with the journal rather than merely equal to
   a stored constant.

Criterion 5 matters for verifier soundness: it is computed at grade time from
the inputs rather than trusted from a stored value, so the suite cross-validates
its own answer key by a second, independent route.

No range or tolerance is used anywhere. The problem has exactly one correct
output, the generator knows it by construction, and any deviation — a single
character misplaced by an off-by-one in the offset conversion — is a fail. This
is deliberate: near-miss answers are precisely the failure mode the task is
designed to expose, and accepting them would defeat the purpose.

The reference solution scores reward 1.0 against this suite; an empty or no-op
submission scores 0. The answer cannot be looked up, guessed, or hardcoded — it
is a specific multi-kilobyte document that exists only in this task's generated
fixtures.

## 4. Category and sub-category justification

**Category — File and Media Operations.** The task operates entirely on files:
it reads a text document and a journal file from disk and produces a text file
whose byte-exact content is the deliverable. There is no service, no dataset
analysis, and no software to build — the artifact under manipulation is the text
file itself.

**Sub-category — Text editing and manipulation.** The task is text editing in
the most literal sense available: the entire problem is a record of editing
operations — insertions and deletions at character offsets — that must be
understood and reversed. The reasoning is about text coordinate systems,
character encoding boundaries, and the semantics of edit operations, which is
the substance of this sub-category rather than an incidental detail. It is not a
parsing, format-conversion, or search-and-filter problem; nothing is being
transformed into another format. It is manipulation of a text document's content
by reasoning about how that content was edited.
